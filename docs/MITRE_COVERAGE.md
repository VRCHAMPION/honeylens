# MITRE ATT&CK coverage

> Generated by `scripts/gen_mitre_coverage.py` from `src/honeylens/mitre/rules.yaml`. Do not edit by hand.

**What:** which ATT&CK (Adversarial Tactics, Techniques, and Common Knowledge) techniques HoneyLens can
recognise in attacker commands. **Why:** mapping raw commands to a shared vocabulary lets you compare
your honeypot with threat reports and explain findings in a SOC (Security Operations Centre).

* ATT&CK version: **Enterprise v19.2** (official STIX, SHA-256 `dc1639caa5501d720e280cf1cbd8fbe009884a0c9b3e6e9ed9d0c25166c3d8f4`)
* Rules: **60** across **9 tactics**
* Distinct techniques covered: **45**
* Coverage: **8.2%** of the 552 active (not revoked/deprecated)
  techniques in the tactics we cover. Most of the rest are Windows/cloud/network techniques an SSH
  honeypot can never see, so this number is a planning aid, not a grade.

**v19 note:** ATT&CK v19 split *Defense Evasion* into **Stealth** (TA0005) and **Defense Impairment**
(TA0112). The classic "defense evasion" category is covered by both. *Resource hijacking* is
T1496.001 Compute Hijacking under **Impact**.

## How the rules are kept honest (all automated in `tests/test_rules.py`)

* every rule has positive examples that MUST match and negative examples that must NOT,
* unknown, revoked and deprecated technique IDs are rejected at startup (the pipeline will not run),
* the tactic must belong to the technique in the snapshot,
* every regex is timed against hostile 4 KB inputs (ReDoS check),
* commands that match nothing are stored with `mapped = false` and listed in the `v_unmapped_commands`
  view, the Credentials & Commands dashboard and the weekly report, so new rules can be written.

## Adding a rule

1. Pick the technique on attack.mitre.org; check it is not revoked/deprecated in v19.2.
2. Add a YAML entry with id, regex, technique, tactic, confidence, rationale, positive and negative examples.
3. `pytest tests/test_rules.py` then `python scripts/gen_mitre_coverage.py`.
4. Re-score old sessions: `docker compose exec pipeline honeylens-pipeline --recompute`
   (re-scores sessions; matches are stored at ingest time, so new rules apply to new events).

## In short

Commands are mapped to ATT&CK with YAML regex rules validated against a pinned official snapshot. When
upgrading to v19 the validator rejected three revoked techniques, which is exactly why the check exists.
Unmatched commands are tracked so coverage grows from real data.
